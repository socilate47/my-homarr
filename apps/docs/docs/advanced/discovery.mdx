Homarr can discover Proxmox guests and add their web services to a dashboard automatically. Each guest runs a small discovery agent. The agent reads its own network interfaces, listening endpoints and Docker metadata; it does not scan other machines.

## Choose Proxmox and a dashboard

1. Add a Proxmox integration in **Manage → Integrations**. Its API identity needs permission to read cluster resources.
2. Open **Manage → Discovery** and select the Proxmox integration and destination dashboard.
3. Enable discovery and choose **Save discovery settings**.
4. Choose **Sync Proxmox now** for the first inventory update.

The **Proxmox discovery** background task refreshes inventory every minute by default. A new VM or LXC container appears as **Agent needed** until its own agent reports. The destination board needs an empty section and at least one layout; a board created through Homarr has these automatically.

## Install the guest agent

The Homarr image built from this checkout includes the installer and Linux amd64/arm64 binaries. They are served from `/api/discovery-agent/`, so no GitHub release is needed. For local Node development, run `bash tools/homarr-discovery-agent/prepare-homarr-assets.sh` before starting Homarr.

On the Discovery page, choose **Show install command** for a guest. The command contains the guest's resource ID, name, Homarr URL and enrollment token. Run it **inside that VM or LXC container**. If the displayed browser URL is not reachable from the guest, replace it with your internal Homarr URL.

For a local binary, run the installer from this checkout:

```bash
sudo HOMARR_URL=https://homarr.example.com \
  HOMARR_DISCOVERY_TOKEN=the-token-revealed-in-homarr \
  DISCOVERY_RESOURCE_ID=qemu/100 DISCOVERY_NAME=media-server \
  HOMARR_AGENT_BINARY_URL=/path/to/homarr-discovery-agent-linux-amd64 \
  bash tools/homarr-discovery-agent/install-agent.sh
```

The installer creates `/etc/homarr-discovery-agent/agent.env`, installs a systemd unit and enables it at boot. The directory and token file are restricted to root. Non-interactive installation requires environment values; interactive installation prompts for missing values. The default resource type is `qemu`; set `DISCOVERY_TYPE=lxc` for a container.

The Docker image sets `HOMARR_DISCOVERY_ASSET_DIR=/app/discovery-agent` for its included downloads. A native server can override this directory with `HOMARR_DISCOVERY_ASSET_DIR`; otherwise Homarr reads `public/discovery-agent` relative to its working directory. Download routes only serve the installer, the two supported binaries and `SHA256SUMS`.

The agent detects its IP addresses automatically and reports every 60 seconds by default. Set `DISCOVERY_ADDRESS` to one of the guest's addresses when it has multiple LAN interfaces. Set `DISCOVERY_INTERVAL` to change the reporting interval, from `10s` to `24h`.

A guest is shown as offline if no heartbeat is received for three reporting intervals. This is separate from the existing application reachability indicator, which checks whether Homarr can reach the application URL.

## Services and dashboard tiles

The agent reports known local web listeners bound to a non-loopback address. With Docker installed, it reads published TCP endpoints and recognizes known web ports inside the container even when the published host port is different. Use labels to include another explicitly selected web service and choose its metadata:

```yaml
labels:
  homarr.discovery.enable: "true"
  homarr.discovery.name: "Grafana"
  homarr.discovery.icon: "grafana"
  homarr.discovery.group: "Monitoring"
  homarr.discovery.protocol: "http"
```

Use `homarr.discovery.enable=false` to exclude a container. Names inferred from port numbers are suggestions; a TCP listener alone does not prove the identity of an application. Unknown host TCP ports are not automatically turned into HTTP links. Docker labels currently supply names, icons and protocols; the group label is retained as metadata and does not create dashboard sections automatically.

New reported web services become app tiles on the chosen board. Different ports on the same IP become separate links. Repeated reports do not create duplicate tiles, and IP changes update URLs still managed by discovery.

For a web app running directly on Linux on a custom port, configure the agent with `DISCOVERY_WEB_SERVICES`, for example:

```bash
DISCOVERY_WEB_SERVICES='[{"name":"My frontend","port":5173,"protocol":"http"}]'
```

Pass this JSON value to the installer. The agent detects the address and reports the declared service only when the port is listening on a non-loopback interface. Entries require a name and valid port, with protocol `http` or `https`; omitted protocol defaults to `http`. Duplicate port declarations are rejected.

You can edit the app name, upload an icon through the existing icon picker, and move the tile. Reports preserve these choices. If you manually change an app URL, discovery keeps that override. Removed tiles stay removed; use **Restore tile** in Discovery to add them again, including when the guest is offline. Missing or offline guests retain their inventory and existing tiles.

Changing the destination board keeps existing tiles on the previous board. Use **Restore tile** for an existing service to add it to the new destination; future new services appear automatically there. Disabling discovery stops synchronization and rejects agent updates without deleting apps or tiles.

## Tokens

Routine discovery queries do not return the enrollment token. Administrators can reveal it explicitly. Rotating it requires confirmation and makes installed agents stop reporting until their token configuration is updated. Changing the selected Proxmox integration also rotates the token, preventing old agents from silently joining a different inventory.

## Docker agent deployment

The Compose example uses host networking and the host Docker socket. Configure the required variables in `.env` before starting it. Access to the Docker socket is privileged, even when its filesystem mount is marked read-only; run this agent only on guests you administer.

## Live wallpapers

Open **Board settings → Background** and upload an image, MP4 or WebM video, up to 32 MB. Uploaded videos are detected using stored media type, so extensionless media URLs work. External MP4, WebM and Ogg video URLs also work, including URLs with query strings.

Video backgrounds loop silently. The wallpaper control pauses or resumes playback. Videos pause while the page is hidden and respect reduced-motion preferences unless you explicitly choose to play. Icon uploads remain image-only.
